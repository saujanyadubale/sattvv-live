# SAT-V&V v0.4 — temporal retesting experiment protocol

**Status:** completed simulation-only research pilot; no experimental hardware or flight qualification. All limits, fault models, warning thresholds, and action costs are illustrative.

## Question and hypothesis

Research question: **Can verification policies that choose *when to repeat a check*, in addition to which test to execute, detect faults that emerge mid-campaign more efficiently than fixed or one-pass testing?**

Specific comparison: `temporal_adaptive` versus `temporal_blind` isolates the marginal effect of **observed warning signals**, while `scheduled_retest` isolates the value of **preplanned repetition**. All strategies run against exactly the same underlying dynamic spacecraft model and test catalog, with the same fault injection schedule and budget cap. Different actions create different physical trajectories, so these are matched *scenarios*, not identical physical states or sensor-noise draws at every time instant.

## Strategies

**v0.3 controls retained exactly:** `fixed`, `random`, `model_fixed`, `adaptive`. They run each chosen test once, then stop at the first requirement failure or when no fitting test remains.

**v0.4 new:**

1. `scheduled_retest` — static, fault-independent patrol of existing tests. Inserts the low-cost T01 system health check periodically and repeats the patrol. It does not use telemetry to choose its order.
2. `temporal_blind` — weighs never-checked requirements, age since prior requirement checks, test criticality, cost, and recent-use cooldown; **ignores** risk-warning values when choosing.
3. `temporal_adaptive` — identical selection formula plus subsystem warning weights extracted from observed voltage, thermal sensor disagreement, temperature and active downlink latency. Ground-truth fault type, severity and start time remain hidden from selection.

For test `i`, a simplified utility is:

```text
U_i = (3.3 * #never_checked + 2.1 * criticality
       + 2.6 * mean(clipped age / 360 s)
       + 1.35 * observed_warning_weight
       - 1.15 * #previous_executions
       - short_term_repeat_penalty) / (test_cost_minutes ^ 0.68)
```

All coefficients are **heuristic starting assumptions** and have not been learned, optimized or calibrated on an independent dataset. `temporal_blind` uses warning weight zero. An explicit one-minute `WAIT` is allowed if all eligible checks are recently measured or the best score is below a nominal utility threshold 3.0 and no risk warning requires attention. A wait advances simulated state and records passive telemetry but **cannot detect a fault**: detection only counts from a failed requirement predicate during a completed test. This distinction is crucial: a displayed alarm or suspicious measurement is not itself a verification failure in the metric.

All methods share the same test executor and nominal requirement thresholds. Costs are catalog test durations in simulated minutes, with readings sampled every 10 simulated seconds, not real processing or communications latency. No action can exceed the allocated time budget. Navigation between modes remains instantaneous; physical orbital/eclipse cycles are not implemented.

## Experimental factors

- Fault families: ten synthetic fault mechanisms plus one `none` healthy control.
- Onset: `0 s` (present at first test) or `600 s` (introduced at minute 10).
- Budget: `12`, `20`, `26`, `33` simulated minutes.
- Normal run: severity `1.0`, state of charge `0.80`, constant sunlight, 10 fixed seeds `0..9`.
- Paired cells: 10 faults × 10 seeds × 7 policies = 700 faulty campaigns per budget/onset, plus 70 healthy controls.
- Additional **limited sensitivity**: severity `0.7`, state of charge `0.80`, continuous eclipse (`sunlit=False`), five seeds. This was checked after prototype development; **not a held-out real-world validation set**.
- Primary outcome: percentage of faulty campaigns with at least one requirement failure *observed by a completed test*.
- Companion metrics: fraction of healthy controls with failed requirements, executed test count, repeat count, simulated minutes waiting, budget usage, detection completion time, checked requirements.
- Plot uncertainty bands: paired hierarchical bootstrap resamples fault families and seeds 400 times, preserving all policy outcomes on matched scenarios. These intervals describe model-library variability only; ten hand-authored fault families are not an unbiased sample of real spacecraft failures.

## Primary results (10 seeds × 10 fault types)

**20-minute verification budget**:

| Policy | Onset at 0 min | Onset at 10 min |
|---|---:|---:|
| Fixed | 67% | 50% |
| Random | 61% | 34% |
| Model-fixed | 70% | 10% |
| v0.3 adaptive | **100%** | 20% |
| Scheduled retesting | 70% | 20% |
| Temporal without warning weights | 50% | 50% |
| v0.4 temporal + telemetry | **90%** | **65%** |

The exact random figure can be verified from `temporal_summary.csv`; this table must remain consistent with regenerated CSV if the benchmark is changed.

**At 26 minutes:** temporal + telemetry yields 100% immediate and 80% delayed detection versus v0.3 adaptive 100% immediate and 30% delayed.

**At 33 minutes:** temporal + telemetry yields 100% immediate and 98% delayed versus v0.3 adaptive 100% immediate and 70% delayed.

**Healthy controls:** zero observed false failures in the cells tested at these nominal settings. This does **not** establish a zero false-alarm rate in general; constraints and noise in the emulator are highly simplified.

**Weak-fault/eclipse sensitivity (five seeds):** at 20 minutes, the temporal + telemetry policy has 70% immediate / 64% delayed detection, versus v0.3 adaptive 80% immediate / 20% delayed. These are additional synthetic tests under one alternative setting, not proof of cross-platform robustness.

## Interpretation and failure analysis

1. **Temporal testing helps specifically when the fault starts late**; repeating or postponing checks allows the policy to find defects after initial inspections.
2. **Telemetry signals matter beyond repetition** in this toy library: at delayed onset + 20-minute budget, temporal with risk weights obtains 65%, temporal without risk weights 50%, and scheduled retesting 20%. CIs span a wide range; avoid claiming a statistically significant or universal advantage.
3. **The new controller can lose on early faults** because it spends effort on already-covered domains or tests with less favorable initial order. At budget 20, v0.3 adaptive yields 100% while temporal + telemetry yields 90%.
4. **Fault-specific limitations:** at delayed onset + 20-minute budget, thermal runaway, overcurrent and payload enable failure often evade the new temporal controller. Some physical degradations require an observation window, operating mode or threshold crossing beyond the campaign horizon. Shorter budgets (12 min) do not favor temporal retesting.
5. Simulator/test co-development creates an optimism risk: warning rules and fault models were created together. Broader injections, time-varying sunlight, sensor noise models, component tolerances, stochastic resets, and independent physics models are needed before using any performance claim outside this research mock-up.

## Reproduction

```bash
conda activate satvv
python -m unittest discover -s tests -v
python -m satvv verify-temporal --fault undervoltage --fault-start 600 --budget 20
python -m satvv bench-temporal --seeds 10 --out results/v0.4
python -m satvv bench-temporal --seeds 5 --severity 0.7 --sunlit no \
  --out results/v0.4/stress_eclipse_weak
python -m satvv serve --port 8765
```

The last command opens the v0.4 local UI at `http://127.0.0.1:8765`. The original v0.3 API remains accessible at `/api/compare` and its unmodified comparator remains in the source. v0.4 uses `/api/compare-temporal`. Everything works locally on the Python standard library; matplotlib is only required for saving PNG benchmark plots.
