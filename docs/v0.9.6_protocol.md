# v0.9.6 protocol — Randomized active verification

## Hypothesis

Requirement-level signatures and access to telemetry sampled *during* each verification test may improve identification of fault-specific evidence. Randomized fault activation, recurrence and combinations should expose limitations absent from curated single-fault demonstrations.

## Testbed

20 executable procedures, simulated EPS–thermal–OBC–COMMS–payload and simplified single-axis ADCS. The solver and test procedures remain synthetic and not calibrated to flight hardware. Every method starts from an identical seeded generated challenge but receives its own independently simulated spacecraft trajectory because executed tests can alter state.

### Scenario generation

- `control`: no fault injected; normal temporary electrical load is allowed.
- `single`: exactly one mechanism.
- `mixed`: one or two different mechanisms.
- `stress`: two or three mechanisms, with optional recurrence and transient normal electrical loading.

Faults include battery-resistance increase, thermal sensor drift, heater fault, radio packet-loss bursts, gyro bias, wheel weakness, and star-tracker dropout. Scenario seed fixes all conditions. **Fault-generation probabilities are arbitrary engineering assumptions, not spaceflight incidence estimates.**

### Diagnosis

Each completed procedure contributes its individual requirement outcomes. Each (hypothesis, requirement) pair has a transparent, hand-specified Bernoulli failure signature (`satvv/diagnosis_v096.py`). Bayesian updates use separate outcomes, with downweighted PASS evidence to reduce repeated test overconfidence. Nevertheless, outcome independence is violated and reported weights are not calibrated.

### Communications warnings

During link tests, record sample timestamps and max packet loss. Monitoring warns when packet loss exceeds 10%. This is kept distinct from verification outcome: the requirement check can only fail based on an actually executed procedure's sampled measurements.

### Audit

Verify recorded policy provenance, chronology, within-test sample intervals, numerical measured-limit consistency when available, and agreement between window monitor status and sampled peak. Not all qualitative/boolean requirements expose numerical detailed samples, so the audit does not independently prove physics validity.

### Benchmark design

Generate paired seeds per difficulty and policy, under the same 30-minute budget. For `control` record verification false-failure rate; for faulty difficulties record detection rate and *partial match* of highest-ranking single-cause hypothesis with any injected fault mechanism. A partial match is **not** diagnosis of all faults. Report results per difficulty, no pooled headline without stratification. Add more unseen physical models and external experimental data before making generalization claims.

### Required regression checks

- Random generator reproducibility and difficulty bounds
- Independent policies see identical hidden scenario parameters
- Oracle data absent from telemetry and decisions
- Healthy negative controls
- Requirement-level packet-loss failure moves the radio-fault hypothesis ahead of healthy
- Fault onset inside link-test sampling interval is recorded
- Deliberate interval tampering triggers evidence-audit failure
- Input/HTTP validation and browser replay state transitions

## Known gaps

The risk-informed test scheduler still uses handcrafted weights. Diagnosis is categorical and cannot identify multiple simultaneous causes jointly. Some alarm types remain visible only in selected test modes. No learned model retraining or externally calibrated uncertainty is introduced by v0.9.6.
