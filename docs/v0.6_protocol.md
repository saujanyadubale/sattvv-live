# SAT-V&V v0.6 — Forecasting, calibration, and verification fixes

## Research question

Can a causally computed 2/5/10-minute forecast of spacecraft bus voltage or equipment temperature anticipate future specification-limit violations under changing synthetic operating conditions, and does a learned forecasting model outperform simple persistence, physics, and linear-trend baselines?

The software is a **synthetic uncalibrated simulator**. A future warning is **not** an executed verification FAIL, physical-fault proof, root-cause diagnosis, or operational remaining-useful-life guarantee.

## Architecture

- Same v0.5 coupled EPS–thermal simulator and all **16** executable verification procedures.
- Same **seven** verification scheduling strategies, with a corrected truly offline `model_fixed` order.
- Dedicated forecasting module `satvv/forecast_v06.py`. It does **not** feed predictions into the test scheduler; information-gain test selection is future work.
- Causal features: last 180 seconds of observed voltage, temperature and SOC trends; current charge, load, solar, current, mode, sensor discrepancy and nominal-voltage residual. **No future samples or hidden fault labels** enter the feature vector.
- Forecast targets: `bus_voltage_v` and `temperature_c` exactly **120 / 300 / 600 simulated seconds ahead** (not the minimum/maximum anywhere inside the window). These are distinct from requirements on the complete test trajectory.

## Four forecasting methods

1. **Persistence:** future measurement = latest observed measurement.
2. **Nominal physics extrapolation:** frozen residual/current load + battery energy balance or single-node thermal dynamics, with fixed current operating conditions. It is not an oracle of future load/eclipses.
3. **Causal linear trend:** least-squares fitted slope using last 180 s, with an explicit bound on extrapolated slope to control instability.
4. **Gradient-boosting regressor:** scikit-learn `HistGradientBoostingRegressor`, separate models for voltage and temperature, using the same observed feature vector.

The fitted models are not Transformers, LSTMs, GRUs, or learned test-selection policies. Deep models would require enough independent fault scenarios and real telemetry to justify complexity.

## Data partitioning

- Training: simulated campaign seeds `100+` (default 4 seed groups × 7 scenarios = **28 campaigns**), supervised by the **future telemetry measurement** available to the offline trainer.
- Calibration: seeds `500+` (**28** independent synthetic campaigns), never used to fit the regressors.
- Evaluation: seeds `900+` (**28** independent campaigns) with changed fault onsets and severities, never used to fit or calibrate the regressors.
- All splits share the **same 7 handcrafted scenario families**. Held-out campaigns do not equate to unseen fault mechanisms or real-world validation.
- Adjacent forecast windows overlap in time. **Rows are not independent**, therefore campaign-level (not row-level) summary metrics are reported; more runs would be needed for robust uncertainty estimation.

## Uncertainty interval

For each calibration campaign, compute the **maximum absolute error** of its entire eligible prediction trajectory. With 28 such scores, the empirical 90% split-conformal rank is `ceil((28+1)*0.9)=27`. The resulting half-width forms the symmetric band `prediction ± width` for a new campaign.

Under exchangeability of complete campaigns this construction is meant to target **simultaneous whole-campaign coverage**. The changed evaluation scenarios challenge exchangeability; the nominal 90% target is **not guaranteed** after distribution shift. We report actual simultaneous campaign coverage and point coverage separately, with neither advertised as calibrated probability of a particular future event.

## Forecast and verification semantics

- Forecast warning: predicted value at `t + horizon` is outside the current requirement limit. No failure assertion is made until an executed check actually fails.
- Voltage event: predicted or realized value **below 6.70 V**. Thermal event: **above 70°C**.
- Evaluation eligible for event forecasting: point is not already in violation at issuance. Compare predicted future violation with the **actual future sample**, and report precision/recall only when positives/predicted positives exist.
- If a metric's denominator is zero it is `null` / blank, not a fabricated 0% success.
- `first_warning_lead_s` is calculated **only for correctly forecast future-limit violations**, avoiding credit for unrelated false warnings.
- Test scheduler policy and forecasting are **separate experiments** in v0.6.

## Corrections relative to v0.5

1. `model_fixed` in coupled verification now commits a requirement-coverage greedy schedule **before campaign execution**. It no longer recomputes ordering from previous test outcomes. Baseline numbers can change; do not compare v0.5 and v0.6 detection percentages without rerunning all policies.
2. Dynamic current specification uses `REQ-EPS-I <= 1.30 A` in **article `SATVV-DYNAMIC-TOY-06`**, matching the dynamic executor and simulator. The historical v0.1 static emulator has a distinct `2.60 A` toy requirement, which remains unchanged for old result reproduction. The dynamic traceability matrix is regenerated in `docs/v0.6_dynamic_traceability.csv` rather than silently rewriting legacy data.
3. The T14 load-step check now uses **absolute voltage prediction error** (`abs(predicted - measured) <= 0.26 V`), consistent with the requirement text. The old signed comparison could falsely pass an unexpectedly high measured voltage.
4. The forecasting physics baseline uses the actual nominal toy simulation thermal constants (`C=260 J/K`, `k=0.075 W/K`, ambient 18°C), rather than unrelated illustrative coefficients.
5. Future labels are exposed only to trainer and offline evaluator; browser and forecast outputs omit fault ground truth.
6. Added regression tests for temporal leakage, reproducibility, source separation, forecasting APIs, preplanned baseline and specification mapping.

## Metrics and limitations

- Forecast MAE in V and °C, *macro-averaged across campaigns*.
- Forecast-event precision/recall for true, **sampled future** violations; note event rarity.
- Campaign-wide ML interval coverage and point coverage on held-out seeds with shifted fault settings.
- Correctly forecast warning lead time (only when an eventual crossing was recorded).
- Further constraints: simplified power/thermal model, no physically calibrated battery aging, no orbital simulation, no independent hardware or real telemetry; learned model may memorize scripted fault templates. Warnings may be false positives, and predictions are not safety decisions.

## Reproduce

```bash
conda env create -f environment.yml  # or activate existing satvv environment
conda activate satvv
python -m unittest discover -s tests -v
python -m satvv bench-forecast --train-seeds 4 --calibration-seeds 4 --eval-seeds 4 --horizon 300
python -m satvv forecast-v06 --scenario heater_fault --mode PAYLOAD --signal temperature_c --horizon 300 --out results/v0.6/example_thermal.json
python -m satvv forecast-v06 --scenario resistance_ramp --mode PAYLOAD --signal bus_voltage_v --horizon 300 --out results/v0.6/example_voltage.json
python scripts/plot_v06.py
python -m satvv serve
```
